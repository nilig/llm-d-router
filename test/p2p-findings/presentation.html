01 · What's implemented and working

The end-to-end P2P path is in place

A request that misses locally can pull its KV prefix from a peer instead of recomputing it. The routing, injection, and connector pieces are wired and firing:

EPP→ sets source header Sidecar→ injects kv_transfer_params.p2p vLLM connector→ lookup + NIXL pull from peer

EPP producer

Routes by cache and sets the source host:port when a peer out-caches the computing pod. Merged (#1924).

Sidecar injection

Reads the header, injects the p2p transfer params into the vLLM request. In review (#1937).

generic_p2p connector

OffloadingConnector + a p2p secondary tier over NIXL; lookup/serve/pull between peers.

PD multi-tier

Disaggregated prefill/decode with tiered offload; the NIXL PD path. Merged (#1888).

The data path itself is correct

Tested directly — one producer, several consumers, pulling straight over the p2p tier with no benchmark load. The mechanism does what it should:

  • Pulls fire and the producer serves 100% of the transfers it starts (142/152 on the fix build; 184/184 in earlier 60-way runs) — the serve path does not drop or stall.
  • Lookups resolve, transfers complete, and prefixes are reused across pods.
  • Exercised across topologies: PD tiered, P2P without PD, P2P with PD (NIXL), and P2P with PD multi-tier.
What "correct" does and doesn't mean here This is the data path behaving correctly in a direct test — with Defect 2 fixed. It is not a claim that the connector is fine standalone: on unmodified branch code it crashes under concurrency even in this direct test (Finding 2). And a correct data path still loses on throughput under load (Finding 1). "Correct" = the pull/serve mechanism does the right thing; it does not mean fast or crash-free as shipped.

02 · The benchmark that started this

With P2P on, throughput collapses

Same routing, same workload, one difference: whether the pod pulls the prefix from a peer (on) or recomputes it locally (off).

Turning on the feature that's supposed to save work makes it ~2× slower, with a quarter of requests failing and tails in the tens of seconds. That's the question I chased: why does P2P lose?

03 · Finding 1 — throughput

Root cause · upstream vLLM (kv_offload / tiering)

The pull runs on the scheduler thread and starves the GPU

During the P2P-on run the GPU is idle the whole time — Running ≤ 5 reqs, KV cache usage ≤ 4%. It's not compute-bound and not KV-bound. Requests simply aren't being admitted to the GPU.

Ablation ladder — each row keeps more of the P2P path

Recompute (off)——1346 tok/s

+ Lookup round-trip (HIT→MISS)yes—1291 tok/s
+ Transfer (normal P2P)yesyes690 tok/s

The EPP header and sidecar cost nothing. The full lookup round-trip costs nothing (1050 lookups resolved, throughput held). Adding the pull / promotion halves throughput.

Confirmed independent of the crash: on the Defect-2 fix build (crash gone, more pulls firing) p2p-on is 567 tok/s vs 1346 off, GPU still idle, 0 crashes. Fixing the crash does not fix throughput.

Why

The NIXL data movement is async. The cost is the coordination around it, synchronous on the scheduler thread: manager._poll_once runs every engine step, and for each session it dispatches wire messages, serves inbound fetches via write_blocks, and polls the transport. On top of that, a HIT defers its request (RETRY) out of Running until the load round-trip finishes. So while the mesh pulls and serves, the scheduling loop can't keep the GPU fed.

Upstream vLLM, not the branch _poll_once, the _initiate_promotion deferral (base TieringManager), and the fetch/transfer path all live in upstream vLLM main (vllm/v1/kv_offload/tiering), not in the generic_p2p branch. The branch runs within this architecture and extends the p2p manager, but the design that starves the GPU — data-plane coordination on the scheduler thread — is upstream. So the fix is an upstream concern, and it affects anyone using the KV-offload p2p tier, not just this branch.
Fix direction Move the P2P data-plane coordination — dispatch, serve/write_blocks, transport polling — off the scheduler thread onto a dedicated background thread, leaving only a non-blocking handoff on the scheduling path.

04 · Finding 2 — the blocker

Root cause · generic_p2p branch

An assert crashes EngineCore under concurrency

Before throughput even matters, P2P can't run under load. The symmetric-P2P lookup phase — flush_pending_lookups and its assert — is a branch addition, not in upstream (upstream main's client.py is 210 lines with no lookup phase; the branch's is 378). It assumes one LookupMsg per request and asserts it. Chunked prefill and reschedule violate that — a request's hashes get registered across several scheduler steps — so the assert fires:

File ".../p2p/session/session.py", line 218, in flush_pending_lookups
    self._client.flush_pending_lookups()
File ".../p2p/session/client.py", line 237, in flush_pending_lookups
AssertionError: LookupMsg already sent for kv_request_id=hp-28315-530649165

Reproduced on unmodified generic_p2p branch code (no local patches) under an 80-way concurrent hammer: 2 of 4 pods crashed and restarted, each on this assert taking down EngineCore.

Fix — validated Allow more than one LookupMsg per request — send the late hashes instead of asserting (a 3-line change removing the assert). The server queues inbound lookups per-message, so it accepts the second LookupMsg. Under the same 80-way hammer: 0 crashes (vs 2 of 4 pods before), no new errors, and p2p still fires (152 hits, 142 transfers, 0 failures).

05 · Summary

Two defects, different owners

P0 · fixed   Crash — flush_pending_lookups assert  · generic_p2p branch

The symmetric-P2P lookup phase is a branch addition. Gated everything: P2P couldn't survive concurrent load. Fix = send the late hashes (allow >1 LookupMsg/request). 3-line change, validated — 0 crashes, p2p intact.

P1   Throughput — coordination on the scheduler thread  · upstream vLLM

The ~2× loss and the idle GPU. Rooted in the upstream KV-offload/tiering data plane, not the branch. Fix = move the data plane off the scheduling critical path. Architectural, upstream.

Neither is in the router — the EPP producer and sidecar are exonerated by ablation. Within the connector the two split cleanly: the crash is the generic_p2p branch (its lookup phase), and the throughput cap is upstream vLLM (the tiering data plane on the scheduler thread). The mechanism is sound; what's left is one branch fix and one upstream architectural change.

How to reproduce

  • Crash: unmodified branch code, 4 pods, warm one with ~300 × 4k-token prefixes, pull concurrently from the others (80 workers). Pods crash at client.py:237.
  • Throughput: bench-ws400 through weighted-random routing, P2P on vs off; watch Running/KV usage — the GPU idles under P2P. Ablation via two one-line manager.py patches.
